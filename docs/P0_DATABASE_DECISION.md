# Quarzion P0 数据库决策

决策日期：2026-08-20（Asia/Shanghai）  
状态：已采用

## 结论

P0 正式化使用一套统一的 SQLite/D1 兼容数据库，客户后台与管理后台挂载同一个正式数据卷。现有前台库与管理端库保持只读归档，不直接升级为正式客户库，也不把演示数据复制进正式库。

## 为什么现在选择它

- 当前生产环境是一台服务器，SQLite 的单机事务、WAL、外键和备份能力足以支持首批真实客户。
- 两个现有应用已经使用 SQLite/D1 风格接口，改造范围更小，能优先解决登录、租户隔离和权限问题。
- 不依赖新的外部数据库账号、网络或供应商，可在现有服务器上完成恢复演练和回滚。
- 统一 SQL 保持 D1 兼容，未来可以继续部署到 Sites，也可以按迁移脚本转到 PostgreSQL。

## 正式运行规则

- 正式库文件固定为 `/data/quarzion.sqlite`，前台和管理端使用同一个只命名数据卷。
- 启动时只执行幂等结构迁移；正式迁移中禁止任何演示 Seed。
- 开启 `WAL`、外键校验、5 秒忙等待和 `NORMAL` 同步模式。
- 用户、组织、项目和客户业务数据均由外键关联；项目业务表同时保存 `organization_id`，便于每次接口查询执行租户过滤。
- 开发、演示、生产使用独立文件或独立数据卷，不允许共享。
- 上线前先在全新暂存卷验证空库启动，再在管理端创建首个真实组织。

## 迁移到 PostgreSQL 的触发条件

满足以下任一情况时进入 P3 数据库迁移：

- 需要多台应用服务器同时高并发写入。
- 真实采集任务产生持续写入锁等待，影响客户查询。
- 单库备份、恢复或存储容量不能满足既定恢复目标。
- 需要数据库级行权限、只读副本、跨区域高可用或更复杂的分析负载。

迁移前继续以统一逻辑模型为准，不在两个应用中重新建立第二套客户或项目表。
